# ADR-001: 用药计划采用"单计划多时刻"建模

日期 / 状态: 2026-09-28 / 已采纳

## 背景

docs/05 §2 与 docs/09 Q2 遗留一个实现期决策：一个药品每天早 8 点、晚 8 点各吃一次，
是存两条计划（一行一个时刻），还是一条计划内嵌时刻数组（`times_json`）。
该决策影响任务展开、规则编辑 UI 与统计口径，动工前必须拍板。

## 决策

采用**单计划多时刻**：`medication_schedules.times_json` 存
`[{"time":"08:00","dose":1,"meal":"after"}, ...]`，一个药品的一组同时段规则
（同频率、同时刻集合）对应一行计划；暂停/恢复以计划为单位。

落点：

- `lib/domain/models/schedule.dart` 的 `MedicationSchedule.times`；
- `DoseService.expandTasks` 对每条计划逐时刻展开成 `dose_tasks`（任务 ID
  `{scheduleId}|{date}|{time}` 确定性生成，展开幂等）；
- 加药表单/草稿确认页以"一次编辑一组时刻"呈现。

## 备选与否决原因

**多计划单时刻**（每时刻一行 schedule）：展开逻辑更笨但更简单，逐条计划
独立暂停/恢复也更细。否决原因：用户心智里"降压药每天早晚饭后吃"是一件事，
拆成多行会让编辑页/药箱详情需要把多行聚合成一个概念，聚合逻辑并没有消失，
只是从 DAO 挪到了每个 UI；且计划数量翻倍后提醒分组的取消管理更易漏。

## 后果

- 好处：规则编辑、暂停、统计的聚合口径天然一致；时刻级字段（剂量、餐前餐后）
  仍保留在 `TimeSlot` 内，细粒度不丢。
- 代价：`times_json` 是 JSON 文本列，无法对单个时刻建索引——但我们从不对
  "时刻"查询（任务表已把时刻物化为列），代价为零。
- 重新评估条件：若出现"同一药的不同时刻需要独立暂停"的真实需求
  （如"晚上的药先停两周"），再迁移为多计划单时刻，届时任务展开按计划粒度
  重算即可，历史任务不受影响。
